### 保存の途中で空になる問題は解決したか

6:33 と 6:40 に、同じ問いがあった。結論は、半分だけ解決している、だった。

- 新しい保存は、書き込み失敗で本番ファイルを空にしない。一時ファイルへ書き、成功したときだけ置き換える。
- すでに空、または書きかけのファイルが残っていると、次の起動はまだ会話まで届かない。

「次の起動」は、状態が `IDLE` に戻ることではない。プロセスを起動し、既存の名前を入れることである。ファイルはあるが JSON として読めないので `JSONDecodeError` になる。当時の `main` は `KeyboardInterrupt` しか受けず、名前の読み込みは `while` の外だった。

### 読み込み側に例外処理を足した

6:49 から 6:58。`read_user_local_json` に、保存側と同じ `raise RuntimeError` を足した案を見た。

- `raise` は例外を関数の中で終わらせない。呼び出し元へ渡す。
- ファイルが無いときは `None` で終わる。壊れた JSON は、例外の種類が変わるだけで、起動は続かない。
- その後、読み込み側はメッセージを出して `None` を返す形になった。例外は `main` まで出ない。
- 保存で新しい空ファイルを作る経路は塞がっている。すでに壊れているファイルを次の起動で読んで、会話まで続けるところは残っている。

6:53 の「読み込みに時間がかかりすぎて `RuntimeError`」は、この失敗の説明にはならない。`JSONDecodeError` は、ファイルの中の文字が JSON として最後まで読めないときに出る。時間切れではない。

### 壊れたファイルでも続けるのか、止めるのか

7:03。求めるのは、壊れたファイルでも起動を続けることである。未処理の例外で止めるのは、レビューが「次の起動で落ちる」と呼んでいる状態そのものである。

続けるときのファイルは、空の正常なデータにはしない。ディスク上の壊れたファイルはそのまま残し、今回の会話だけ記憶なしで進む。その次の保存が壊れたファイルを読むと、再び例外が出る。起動を続けるなら、その保存もファイルを置き換えず、例外をループの外へ出さないところまでが同じ失敗である。

`JSONDecodeError` は、中身が全部消えたという意味ではない。末尾が欠けていることが多い。レビューの合格条件も、破損データを空データで上書きしないことである。

7:35。中身をコピーして新しいファイルに載せても、欠けた文字はそのまま入る。`json.load` で読んでから `json.dump` する経路は、読み込みの時点で失敗する。
