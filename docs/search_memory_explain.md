## 3. これまでに実装・検証したもの
- 基本状態遷移：
  IDLE → LISTENING → THINKING → SPEAKING → IDLE
- 空入力はEMPTY状態を経て入力受付へ戻る。
- 登録語句による固定返信。
- 「僕」「私」などを含む発言を記憶候補として抽出する。
- 新しい記憶はリストへ追加し、完全一致する重複は追加しない。
- 新規記憶には「覚えておくね。」、既存記憶には「それは前に聞いたよ。」と返す。
- ユーザー別JSONに名前と記憶を保存する。
- 起動時にJSONを読み、memoriesへ保持する。

保存形式：
{
  "name": "test",
  "memories": [
    "僕は、日大生です。"
  ]
}

## 5. 今回の主目的
保存した記憶を、会話中の質問から検索して返したい。

最終的な利用例：
ユーザー：「昨日話した予定って何だっけ？」
Miroc：「昨日は『土曜日に図書館へ行く予定』と話していたよ。」

ただし、現在のJSONには記録日時がない。
「昨日話した」を扱うには、将来、話した日時と予定の日時を区別して保存する必要がある。
日時検索やLLM導入を先回りせず、まず文字列の部分一致検索を作る。

作業ブランチ名として選んだ名前：
feat/memory-reader-output
※実際の現在ブランチは確認すること。

## 6. 現在目指している役割分担
- main：
  起動時のJSON読み込みと、状態に応じた処理の呼び出し。
- on_thinking：
  検索要求・記憶追加・通常返信を振り分ける。
- search_memory：
  memoriesとqueryを受け取り、一致する記憶をlist[str]で返す。
- reply_to_search_memory：
  検索結果を返信文字列にする。
- on_speaking：
  完成した返信文字列を表示する。

検索関数や返信生成関数では、input・print・JSON保存・状態遷移を行わない。
検索のために毎回JSONを読み直さず、起動時に読み込んだmemoriesを使う。

## 7. 検索処理で整理したこと
search_memoryの意図：
- 空の検索語なら[]。
- queryを含む記憶をすべて集める。
- 見つからなければ[]。
- 元のmemoriesを変更しない。
- ループ内では結果リストへappendする。
- returnは全件を調べ終わってから行う。

最初の一致直後にreturnすると、複数件の検索結果を返せない点を学んだ。

reply_to_search_memoryの意図：
- 0件なら「検索結果がありません。」を返す。
- 1件以上なら"\n".join(search_results)で文字列にする。
- printせず、文字列を返す。
- 全経路で文字列を返すため、戻り値型はstrが適切。
- bodyは文字列なのでreturn bodyでよい。

実ファイルにどこまで反映されているかは確認すること。

## 8. 現在の主な未解決事項
直近の提示コードでは、検索要求をremembered_memoryの有無で判断していた。

概略：
proposed_memory = propose_memory(request)
remembered_memory = reply_remember(proposed_memory)
search_request = request_to_search(remembered_memory)

if remembered_memory is not None:
    記憶追加
elif search_request is not None:
    検索返信
else:
    通常返信

この構成には次の問題がある。
- remembered_memoryは「覚える候補」であり、検索要求ではない。
- 候補があると最初のifへ入り、検索分岐へ到達しない。
- request_to_searchはTrueしか明示的に返さず、それ以外は暗黙のNoneだった。
- boolの判定に「is not None」を使うと、Falseでも条件成立になる。
- 質問文全体を検索語にすると、保存済み文章に部分一致しにくい。

これらは直近の提示コードへの指摘であり、現在の修正状況は要確認。

## 9. 次に決めて実装すること
1. 検索要求として受け付ける入力形式を決める。
   候補例：「覚えてる？ 図書館」
   この形式は提案段階で、確定仕様ではない。

2. 発言requestから検索要求かを判定する。
   記憶候補の有無を判定材料にしない。

3. 発言から検索語だけを取り出す。
   例：「覚えてる？ 図書館」→「図書館」
   検索語が空の場合の動作も決める。

4. on_thinkingでは検索要求を先に判定する。
   検索でなければ、既存の記憶追加・通常返信へ進む。
   「僕」を含む検索質問を誤って記憶として追加しないようにする。

5. reply_to_search_memoryを呼び、作った返信を既存の表示経路へ返す。

## 10. 追加したいテスト
- search_memory：
  0件・1件・複数件、空の記憶リスト、空の検索語、元のリストの保持。
- reply_to_search_memory：
  0件の案内文、1件の文字列、複数件の改行結合。
- 検索要求の判定と検索語の抽出：
  決めた入力形式に沿って正常・境界ケースを確認する。
- on_thinking：
  検索経路へ進み、適切な返信を返す。
  検索質問自体を新規記憶として追加しない。
  既存の挨拶・記憶追加を壊さない。
- 全体：
  保存後に終了し、同じユーザーで再起動して検索できる。
