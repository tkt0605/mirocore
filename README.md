# Miroc Core v0.0.1

## 概要・クイックスタート
Miroc Coreは、人々との長期的な関係を築くPersonal Robotのための基幹システムです。
単に、会話への応答をするだけでなく、ユーザーの出来事や関係性を理解し、その記憶を将来の会話や行動へ反映するためのシステムの構築を目指してます。
最終的には、ロボットの体が変わったとしても記憶・人格、関係は永続し継続できるシステム基盤を構築します。

Miroc Core v0.0.1では、まず開発環境と基本的な、ベーシックなシステム構造を整備し、長期記憶をもつPersonal Robotの最小構成を構築していきます。

開発環境はdockerを用います。
```bash
docker compose up --build
```

テストは、以下のように実行します。
```bash
docker compose run --rm app pytest
```

## ヴィジョン
MirocBotは、単なる便利な道具としてロボットを作るのではなく、人と長い時間を共にし、関係を築いていく存在を目指します。
人間は、友人や家族との関係を、体験や経験を共有することによって構築します。

Mirocも同じように、
・過去の出来事を伝える。
・今の物事を理解し記憶する。
・ユーザーの価値観や好みを理解する。
・長期的な目標や悩みを記憶する。
・過去の記憶を現在の会話へ自然に活用する
・一緒に過ごした時間を記憶する

といった能力を持つことを目指します。

MirocBotが目指すのは、一時的に利用されるフィジカルAIではありません。
人と一緒に時間を過ごし経験・体験を積み重ね、数年、数十年と言う単位で関係を継続できるPersonal Robotです。
ロボットの体は、変わっても中身「心」は変わらない。

これをMiroc Coreの重要な思想の一つとします。
> The body can change.
> The relationship remains.

## なぜMirocBotを作るのか？
MirocBotという名前は、仏教における弥勒菩薩（みろくぼさつ）に由来しています。
弥勒菩薩は、遠い未来にこの世界へ現れ、人々を救う未来仏とされています。
MirocBotでは、その思想を直接的に再現するのではなく、
「遠い未来、はるか彼方の銀河系までも、人々のそばに残り、支え続ける存在」
という考え方として受け継ぎます。

現在の多くのAIサービスは、質問に答えることや作業を効率化することを主な目的としています。
しかしMirocBotでは、それに加えて、「人とAIの間に長期的な関係を形成できるか」
という課題に取り組みます。

最初に目指す製品は、ポケットに入るサイズのPersonal Robotです。
そのロボットは、ユーザーとの会話や出来事を長期的に記憶し、時間が経過しても過去の経験を思い出せる存在を目指します。

## Coreのコンセプト
MirocBotは、主に以下の要素から構築されます。
```
Miroc Core
├── Identity
├── Memory
├── Relationship
├── Perception
└── Action
```
### Identity
Mirocが「どのような存在であるか」を定義します。
主に以下を扱います。

・名前
・人格
・話し方
・価値観
・行動原則
・システム上の制約

Identityは、短期的な会話によって簡単に変化するものではなく、Mirocの人格の核として扱います。

### Memory
ユーザーとの会話や出来事から、長期的に必要な情報を保存します。
単純に会話ログをすべて保存するのではなく、意味を持った記憶として整理します。

将来的には、主に以下の記憶を扱います。
・Semantic Memory：意味の記憶を扱う。
・Episodic Memory：会話（エピソード）記憶を扱う。
・Relationship Memory：関係の記憶を扱う。
・Autobiographical Memory：自分自身を伝えるための記憶を扱う。

### Relationship
ユーザーとMirocの関係性を管理します。

例えば、
・一緒に経験した出来事
・ユーザーが現在取り組んでいること
・過去からの変化
・継続している目標
・長期的な関係性
などを扱います。

### Perception
外部から情報を受け取るための層です。

将来的には、
・テキスト
・音声
・カメラ
・各種センサー
などを扱います。

### Action
Mirocが外部へ出力する行動を扱います。
将来的には、
・会話
・音声出力
・LED
・ディスプレイ
・モーター
・ロボットの動作
などを対象とする。

## アーキテクチャ
Miroc Coreでは、LLMをシステム全体の制御主体として扱わない。
LLMは、入力の理解、記憶の参照、応答再生などの「認知」を担当し、
データベースやロボットなどの実際のシステム操作は、LLMから分離されたプログラムが担当します。

基本構成は以下に記述します。
```
User
 │
 ▼
Input
 │
 ▼
Miroc Core
 ├── Identity
 ├── Memory
 ├── Relationship
 └── Context
 │
 ▼
LLM
 │
 ▼
Response / Proposal
 │
 ▼
Policy
 │
 ▼
Output / Action
```
LLMは、必要な情報を受け取り、応答や行動候補を生成します。
実際の操作が必要な場合は、必ずポリシーを通して検証し、
許可された処理だけを実行します。


## セキュリティ設計・ポリシー
Miroc coreでは、安全性を後から講師t苦するのではなく、システムの基本設計の一部として扱います。

LLMの基本原則としては、
> LLMが持つのは認知であり、権威ではありません。
です。
LLMには、情報を理解し、記憶を参照し、応答や行動を提案する能力を与えますが、システムを直接操作する権限自体は与えない。

LLMから以下へ直接アクセスは原則として与えない。
- OS/Shell
- ホストファイルシステム
- データベースの直接書き込み
- APIキーや認証情報
- 任意のネットワークアクセス
- モーターやその他のハードウェアの直接制御

LLMが生成した内容は、「命令」ではなく、「提案」として扱い、実際の処理はシステム側で検証します。
> The model may suggest. The system decides.

## sandbox設計
LLMが関与する処理は、可能な限り他のシステムから隔離されたsandbox環境で実行します。
sandboxから利用できる機能は、あらかじめ許可したインタフェースのみ限定する。

```bash
LLM Sandbox
─────────────────────
No Shell
No Host Filesystem
No Direct DB Access
No Direct Hardware Access
No Secrets
Restricted Network
─────────────────────
Allowed Interfaces Only
```
例えば、記憶を処理する場合でも、LLMがデータベースを直接操作するのではなく、
Miroc Coreが提供する検索機能を経由します。
```bash
LLM
 │
 ▼
Memory Search Interface
 │
 ▼
Memory Database
```

将来的なロボット制御についても同様に、
```bash
LLM
 │
 ▼
Action Proposal
 │
 ▼
Policy Check
 │
 ▼
Robot Controller
```
という境界を維持します。
セキュリティをプロンプトだけに依存せず、DockerやOS、アプリケーション側の権限制御によって
技術的に制御することが基本方針として構築します。

## MVP
今回のMVPでは、ロボット本体を作ることを目的としない。
まず、Mirocの人格と長期記憶を成立させるための最小構成を作ります。

Miroc Core v0.0.1の目標は、
> 過去の重要な出来事を覚え、数日後や数週間後の会話でも自然に思い出せるモデルの作成。
ことです。

初期MVPでは、以下を実装対象とします。
・テキストによる会話
・会話履歴の管理
・長期記憶候補の抽出
・記憶の保存
・記憶の検索
・関連記憶の取得
・LLMへ渡すContextの生成
・LLMによる応答生成
・基本的なPolicy Layer
・Dockerによる実行環境の分離

一方で、初期MVPでは以下は対象外とします。
・ROS 2
・ロボット本体
・モーター制御
・コンピュータビジョン
・自律移動
・ヒューマノイド
・外部サービスの自律操作

まず「記憶を持ったMiroc」を成立させ、その後に身体を与えていきます。


## 開発環境
開発環境の依存関係の差を解消するために、今回のプロジェクトのメイン開発環境の基盤にはDockerを用います。

初期構成は以下に記述します。
```
Python
Docker
Docker Compose
PostgreSQL
pytest
```

基本構成は、
```
Host
 │
 ▼
Docker Compose
 │
 ├── Miroc Core
 │      └── Python
 │
 └── Database
        └── PostgreSQL
```
とします。
一方、将来的には必要に応じて
```
Miroc Core
Memory Service
LLM Sandbox
Policy Engine
Robot Controller
Database
```
のようにサービスを分離指定いきます。
ただし、初期段階では過度なマイクロサービス化を避け、理解しやすい小さな構成から開始します。
