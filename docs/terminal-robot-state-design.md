# Terminal Robot 状態設計

## 目的

Terminal Robotは、ターミナル上でユーザー入力を受け取り、状態に応じた表情と応答を返す最小のPersonal Robot試作です。

初期MVPは、Miroc Core本体のCLIとは別のエントリーポイントから、DB、LLM、長期記憶、ネットワーク接続なしで起動できる状態を保ちます。

起動コマンド：

```bash
uv run python -m mirocore.terminal_robot
```

## 初期MVPの責務

状態、入出力、表情、応答生成を一つの処理へ集めず、次の責務として分けます。

| 責務 | 現在の配置 | 状態 | 役割 |
|---|---|---|---|
| 状態とイベントの定義 | `terminal_robot/state.py` | 実装済み | `RobotState`と`RobotEvent`を定義する |
| 状態遷移 | `terminal_robot/state.py` | 実装済み | 現在状態とイベントから次状態を決定する |
| 進行制御と入出力 | `terminal_robot/__main__.py` | 実装済み | 入力、イベントの選択、表示、終了を順番に進める |
| 表情と表示プレフィックス | `terminal_robot/expressive.py` | 実装済み | 状態に応じた顔と発話者を表現する |
| 応答生成 | `terminal_robot/reply.py` | 実装ずみ | 固定応答を生成する責務を配置する。現在の固定応答は`__main__.py`にある |

`transition()`は入出力を行わない純粋な遷移関数として保ちます。将来LLMを接続する場合も、状態遷移や実行権限をLLMへ移しません。

## 状態の意味

| 状態 | 意味 |
|---|---|
| `IDLE` | まだ入力を受け付けていない待機状態 |
| `LISTENING` | ユーザー入力を待っている状態 |
| `THINKING` | 入力が確定し、応答を準備している状態 |
| `SPEAKING` | 準備した応答を出力する状態 |
| `ERROR` | 空入力や不正な遷移などの異常を表示する状態 |

状態は「テキストが存在するか」ではなく、Terminal Robotが現在どの処理段階にいるかを表します。

## 正常な状態遷移

基本サイクル：

`IDLE → LISTENING → THINKING → SPEAKING → IDLE`

| 現在状態 | イベント | 次状態 | 物理的な意味 |
|---|---|---|---|
| `IDLE` | `START_LISTENING` | `LISTENING` | 入力受付を開始する |
| `LISTENING` | `CONFIRM_INPUT` | `THINKING` | ユーザー入力を確定する |
| `THINKING` | `REPLY_READY` | `SPEAKING` | 応答の準備が完了する |
| `SPEAKING` | `OUTPUT_DONE` | `IDLE` | 応答の出力を完了する |
| `ERROR` | `ERROR_SHOWN` | `IDLE` | エラー表示後に待機状態へ戻る |

## 入力と終了

- 通常のテキストは`LISTENING`でのみ受け付けます。
- 空文字は`ERROR`として扱い、エラーメッセージを表示してから通常サイクルへ戻します。
- `/q`、`/quit`、`/exit`は`LISTENING`で受け付け、安全にループを終了します。
- `Ctrl+C`による`KeyboardInterrupt`はループ全体で捕捉し、終了メッセージを表示して停止します。
- 同期処理である`THINKING`と`SPEAKING`では、通常のユーザー入力を受け付けません。

## 不正な状態遷移

`transition()`に未定義の状態とイベントの組み合わせを渡すと、遷移表の検索に失敗して`KeyError`が発生します。その時点では、呼び出し元が保持する状態は変更されません。

現在の進行制御では、この`KeyError`を捕捉して`ERROR`へ移し、`ERROR_SHOWN`によって`IDLE`へ戻します。不正な遷移を黙って無視したり、推測で次状態を決めたりしません。

## MVPの完成条件

完成判定は文書上の想定ではなく、実際のテスト結果と手動操作で行います。

| 完成条件 | 主な確認方法 |
|---|---|
| DBなしで起動できる | 手動起動テスト |
| LLMなしで起動できる | 手動起動テスト |
| 4つの基本状態を表示で区別できる | 表示の単体テスト、手動確認 |
| 入力に応じて基本サイクルを遷移する | 状態遷移の単体テスト |
| 応答後に`IDLE`へ戻る | 状態遷移の単体テスト、対話テスト |
| 終了コマンドで安全に終了できる | `monkeypatch`を使った対話テスト |
| `Ctrl+C`で安全に終了できる | `KeyboardInterrupt`を使った対話テスト |
| 非TTY環境ではANSI制御文字を出力しない | 非TTY出力の自動テスト |
| 状態遷移と表示を別々に検証できる | `state`と`expressive`の単体テスト |

テストが存在することと、テストが成功していることは分けて扱います。`collected 0 items`も成功とは扱いません。

## UI技術の方針

初期MVPはPython標準ライブラリとプレーンテキストで成立させます。RichやTextualは、アニメーション、複雑なレイアウト、継続的な画面更新が必要になった時点で、学習コスト、依存関係、テスト容易性、macOS/Linux互換性、非TTY対応、Raspberry Pi移植性を比較して判断します。

TTY固有の表現を追加する場合も、非TTY環境ではプレーンテキストへフォールバックできる設計を保ちます。

## 将来の接続境界

- LLMやChatServiceは応答候補を生成しますが、状態遷移や実行権限は持ちません。
- Memoryを接続する場合は、Terminal UIから直接DBを操作せず、専用のサービスまたはRepositoryを経由します。
- Raspberry Pi、ディスプレイ、音声、LED、モーターなどのOS・ハードウェア依存処理はAdapterとして分離します。
- 顔データとターミナル描画は、表現が複雑になった時点で別々にテストできる境界へ分割します。

## 初期MVPでは扱わないもの

- LLMによる応答生成
- PostgreSQLと長期記憶
- 音声入出力
- モーターやセンサーの制御
- 非同期入力と同時入力
- 入力キュー、自動再試行、タイムアウト制御
- RichやTextualによるフルスクリーンUI

これらは必要性が明確になった段階で、初期MVPとは別の設計判断として追加します。
