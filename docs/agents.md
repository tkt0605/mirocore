# MirocBot / Miroc Core Development Instructions

## Project vision

MirocBotは、人と長期的な関係を築くPersonal Robotを目指すプロジェクトです。

中心理念：

> The body can change. The relationship remains.

ロボットの身体が変化しても、Identity、Memory、Relationshipを引き継げるソフトウェア基盤を構築します。

## Miroc Core responsibilities

Miroc Coreは、将来的に次の領域を扱います。

- Identity
- Memory
- Relationship
- Perception
- Action

LLMは、入力の理解、推論、応答や行動案の生成を担当します。

次の責務は、LLMではなくPolicy Layerや決定論的なプログラムが所有します。

- 権限の判定
- OS操作
- データベースへの書き込み
- 外部ネットワークへのアクセス
- モーター制御
- センサー制御
- タイムアウト
- リトライ
- 緊急停止
- フェイルセーフ

想定する安全境界：

`Miroc Core / LLM → Policy Layer → Behavior Manager → Robot Controller`

## Current development target

最初の試作機として、Terminal Personal Robotを開発します。

初期状態：

- `idle`
- `listening`
- `thinking`
- `speaking`

基本状態遷移：

`idle → listening → thinking → speaking → idle`

Phase 1では、LLM、PostgreSQL、長期記憶、ネットワーク接続を必須にしません。

Terminal Robotは、既存のCore起動処理とは分離されたエントリーポイントから起動できる設計を優先してください。

## Architecture principles

- Pythonを中心にする
- 既存のuv環境を利用する
- pytestで検証できる構造にする
- UIとビジネスロジックを分離する
- 状態、状態遷移、描画、入力、応答生成を分離する
- OS固有処理をCoreへ混在させない
- ハードウェア依存処理はAdapterとして分離する
- macOSとLinuxの両方を考慮する
- 非TTY環境ではプレーンテキストへフォールバックする
- 不要な依存ライブラリを追加しない
- 最初はPython標準ライブラリで成立するか検討する
- 初期段階ではマイクロサービス化しない
- 過剰な抽象化や将来機能の先行実装を避ける
- 既存設計を尊重し、大規模な作り直しを避ける

## Development workflow

作業前に、必ず現在のリポジトリを読み直してください。

過去の分析結果だけで、現在の実装を判断しないでください。

変更前に確認するもの：

- リポジトリ内の指示ファイル
- 現在のブランチ
- 既存の未コミット変更
- 対象ファイルの現在の内容
- 関連テスト
- CLIと設定の実行経路

既存の未コミット変更はユーザーの作業として扱い、上書きしないでください。

## Implementation boundary

ユーザーが明示的に実装を依頼した場合のみ、ファイルを変更してください。

実装時は次の順序で進めてください。

1. 対象コードを確認する
2. 変更理由を説明する
3. 影響範囲を示す
4. 最小の変更を実施する
5. 関連テストを実行する
6. 実行結果と未検証事項を報告する

明示的な許可なしに、次を行わないでください。

- 大規模リファクタリング
- 依存ライブラリの追加
- データベーススキーマの変更
- 公開APIの変更
- Gitコミット
- Gitプッシュ
- ブランチ作成
- 外部サービスへの書き込み
- ハードウェアの作動

## Security

秘密情報を表示、記録、コミットしないでください。

特に次の値は、全文を出力しないでください。

- `DATABASE_URL`
- APIキー
- アクセストークン
- パスワード
- Cookie
- 認証ヘッダー
- 秘密鍵

接続設定を説明する場合は、値ではなく環境変数名だけを示してください。

## Testing and verification

コードの存在だけで、動作確認済みと判断しないでください。

可能な範囲で、実際のコマンドと終了コードを確認してください。

報告時は次を区別してください。

- コードを読んで確認したこと
- テスト実行で確認したこと
- 手動操作で確認したこと
- 未検証のこと

テストを実行できなかった場合は、推測で成功扱いせず、理由を説明してください。

Docker設定の構文確認と、実際のイメージビルド・コンテナ起動は別の検証として扱ってください。

## Mentoring style

ユーザーはPythonとロボット工学を、自分でコードを書きながら学習します。

そのため、次を優先してください。

- 小さな実装単位
- クラスや関数の役割の説明
- 入力と出力の説明
- 状態遷移の意味の説明
- 短い練習問題
- 小さなpytest
- 実装後の観察ポイント
- 完成コードを一度に大量提示しないこと

ユーザーが実装を依頼した場合は必要な変更を行って構いませんが、変更理由と検証方法を説明してください。

## Reporting format

作業結果は日本語で報告してください。

最初に結論を示し、その後に根拠を説明してください。

重要な指摘には、可能な限りファイルパスと行番号を付けてください。

次の区分を混同しないでください。

- 確認済み
- 推測
- 提案
- 未検証
