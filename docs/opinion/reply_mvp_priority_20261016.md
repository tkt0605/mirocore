# `reply.py`最小MVPの推奨整理順序

## 目的

`reply.py`を、単純なキーワード応答から、将来のIdentity・Memory接続へ拡張できる最小の返信生成境界へ整理する。

今回の目標は、次の契約へ段階的に近づけることとする。

> ユーザー名・現在の発言・任意の関連記憶1件を受け取り、決定論的な返信本文を返す。

一度に完成させず、各段階でテストを成功させてから次へ進む。

## 現在確認できている問題

この文書の作成時点では、主に次の問題がある。

- `random.choice()`により、同じ入力でも返信が変わる。
- 挨拶の入力から、別の時間帯の挨拶が返る可能性がある。
- 感情ごとの返信リストからランダムに選ぶため、入力内容と返信内容が対応しない場合がある。
- `request.split()`は、空白を入れない一般的な日本語文や句読点付きの入力を認識しにくい。
- ユーザー名がモジュール内の固定値であり、関数の引数として渡されていない。
- 関連記憶を受け取る契約がまだない。
- `reply.py`を直接検証するテストがない。
- 既存の`test_main.py`は、以前の「入力値を名前として挨拶する」仕様を期待している。

## 推奨する整理順序

### 1. `reply()`を必ず文字列を返す決定論的な関数にする

最初に、現在の発言だけを受け取る契約を安定させる。

完了条件：

- 同じ入力には常に同じ返信を返す。
- すべての入力経路で`str`を返す。
- キーワードに一致しない場合も、フォールバック返信を返す。
- `print()`、`input()`、状態変更を行わない。
- 挨拶、疲労・悲しみ、喜びを、意味の対応した固定返信へ結び付ける。

この段階では返信のランダムなバリエーションを扱わない。

### 2. 最小限の日本語入力規則を決める

高度な自然言語解析は導入せず、MVPで認識する入力の範囲を明確にする。

確認対象：

- `こんにちは`
- `こんにちは！`
- `今日は疲れた`
- `元気だけど眠い`
- どのキーワードにも一致しない入力

完了条件：

- 空白の有無だけで結果が不自然に変わらない。
- 句読点付き入力の扱いが決まっている。
- 複数のキーワードが含まれる場合の優先規則が決まっている。
- 対応範囲外の入力はフォールバック返信になる。

形態素解析ライブラリやLLMは、この段階では追加しない。

### 3. `reply.py`の直接テストを追加する

`main()`経由の統合テストだけに依存せず、返信生成の契約を単体で確認する。

最低限のテスト対象：

- 挨拶への返信
- 疲労・悲しみへの返信
- 喜びへの返信
- 通常のフォールバック返信
- 同じ入力から同じ結果が返ること
- 関数が標準出力へ何も出さないこと

対象テストが成功した後に、全テストを実行する。

```bash
uv run pytest tests/terminal_robot/test_reply.py -v
uv run pytest -v
```

### 4. ユーザー名を外から渡す

現在のモジュール内固定値を、返信生成へ渡される文脈へ変更する。

完了条件：

- `reply.py`が特定のユーザー名をグローバル変数として保持しない。
- 異なるユーザー名でも同じ返信関数を利用できる。
- ユーザー名と現在の発言が別の値として扱われる。
- 起動時の挨拶と通常会話の責務が区別されている。

ユーザー名をどこへ永続化するかは、この段階では扱わない。

### 5. 任意の関連記憶1件を受け取れるようにする

DBや検索機能は実装せず、外部から渡された記憶を返信へ反映する境界だけを作る。

完了条件：

- 関連記憶がなくても返信できる。
- 関連記憶が1件渡された場合は返信へ反映できる。
- `reply.py`自身は記憶を保存・検索・選定しない。
- テストでは固定値の仮記憶を渡して確認できる。

ここで扱うのは「記憶を使う返信」であり、「長期記憶システムそのもの」ではない。

### 6. `__main__.py`との接続を確認する

Terminal Robotの状態と返信生成の意味を一致させる。

期待する流れ：

```text
LISTENING
  現在の発言を確定する
    ↓
THINKING
  reply()で返信本文を生成する
  REPLY_READYを設定する
    ↓
SPEAKING
  add_prefix()と返信本文を組み合わせて表示する
  OUTPUT_DONEを設定する
```

完了条件：

- `reply()`は`THINKING`で1回だけ呼ばれる。
- `SPEAKING`では作成済みの返信本文だけを表示する。
- `reply.py`は`RobotState`、`RobotEvent`、`add_prefix()`へ依存しない。
- `/q`、`/quit`、`/exit`、空入力、`Ctrl+C`の既存動作を壊さない。

### 7. 設計文書を現在の仕様へ同期する

コードとテストが安定した後に、`docs/terminal-robot-state-design.md`を更新する。

確認対象：

- `reply.py`が未実装という記述
- 固定返信が`__main__.py`にあるという記述
- `THINKING`と`SPEAKING`の実際の責務
- `EMPTY`状態と空入力時の遷移
- 新しいMVPの完了条件

## 今回は後回しにするもの

- LLMによる返信生成
- PostgreSQLやファイルへの記憶保存
- 関連記憶の検索・ランキング
- 高度な感情分析
- ランダムな返信バリエーション
- 音声、センサー、モーターとの接続
- 非同期処理

`鬱病`のような重大な内容は、単純な感情キーワードとランダム返信で扱わない。将来、Policyや安全な応答方針を含む別の設計単位として検討する。

## 最小MVPの最終完了条件

- ユーザー名、現在の発言、任意の関連記憶1件を区別して受け取れる。
- 関連記憶は0件または1件として扱える。
- 同じ入力と文脈には同じ返信を返す。
- すべての経路で返信本文の`str`を返す。
- 標準入出力、状態遷移、記憶保存を行わない。
- `reply.py`の単体テストとTerminal Robotの統合テストがすべて成功する。
- DB、LLM、ネットワークなしで動作する。

## Cursorへ依頼するときの制約

- 一度に扱うのは上記の1段階だけにする。
- 現在のコードとテストを確認してから計画する。
- ユーザーが実装するため、完成コードを一括提示しない。
- 修正理由、入力、出力、状態変化、追加すべきテストを説明する。
- 大規模なリファクタリングや将来機能を混ぜない。
